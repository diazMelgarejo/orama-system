## Why this exists, in one paragraph

`query_peer_topology.py` and `probe_lan_peer.py` authenticate peer-to-peer
mesh requests with a shared bearer token. As of the v1 fix (above), that
token is never sent over plain HTTP — but there is still no TLS peer
infrastructure to send it over *instead*. This plan is what closes that
gap: certificate provisioning for LAN peers, a pluggable auth-provider
architecture that keeps the existing bearer token working forever
(grandfathered, never forced to migrate), and a path to stronger identity
(BUZZ/Nostr, OAuth) for operators who want it. AlphaClaw's lack of native
HTTPS is a second, related gap this plan also closes.

## Architecture at a glance

```text
Today (v1, landed):
  [orama-system] --http, no token if unauth'd--> [peer]
  [orama-system] --STOP, never sent--> [peer]   (if a real token exists and transport isn't https)

v2 target:
  [orama-system] --AuthManager (BUZZ > Twitter > Google > Bearer)--https+cert-pinned--> [peer]
                                                                            |
                                                            self-signed cert, TOFU-pinned fingerprint,
                                                            90-day rotation, generated by peer_cert_manager.py

  [orama-system] --https(local proxy)--> [alphaclaw-tls :HTTPS_PORT] --http(loopback only)--> [AlphaClaw]
```

## Decisions (the 13 open questions, answered)

All v1-column answers below are **not implemented yet** — they are the
agreed target for when this plan is picked up, recorded now so the
decision doesn't need to be re-litigated later.

| # | Question | v1 target answer | v2+ |
|---|---|---|---|
| 1 | Certificate provisioning | Auto-generated self-signed (2048-bit RSA) + TOFU fingerprint pinning, `peer_cert_manager.py` | Shared-CA option for hardened deployments |
| 2 | AlphaClaw HTTPS | AlphaClaw has no native HTTPS (Node/Express, HTTP-internal, `trust-proxy` support exists). New `alphaclaw-tls` PT package: local-only HTTPS reverse proxy in front of it | Native HTTPS if AlphaClaw ever adds it |
| 3 | Existing deployments | `PEER_TLS_ENABLED` auto-detects fresh vs. existing install (token exists, no cert dir ⇒ existing); v1 **warns only**, never enforces | v2 removes the flag, enforcement unconditional |
| 4 | Certificate pinning | Yes — TOFU (trust-on-first-use) automatic, `PEER_PINNED_FINGERPRINTS` env for admin pre-seeding | Hard reject on pin mismatch (MITM detection) |
| 5 | mTLS | Server-auth TLS only | Full mutual TLS (client certs) |
| 6 | Token rotation | None — bearer tokens stay long-lived for backward compat | Short-lived (≤1h per RFC 6750 §5.1 guidance) + refresh |
| 7 | Audit logging | Yes — append-only `.orama/audit.log`, HMAC-chained (each entry signs over the previous entry's signature, tamper-evident) | BUZZ-signed entries when available |
| 8 | BUZZ/Nostr dependency | Inline minimal NIP-98 sign/verify, zero new deps (reuses `cryptography`, already transitive via endpoint-policy) | Optional full `nostr` library |
| 9 | OAuth token refresh | On-demand, synchronous, before each request | Background refresh thread |
| 10 | Per-peer auth policy | Mesh-wide uniform provider priority | Per-peer `PeerAuthPolicy` override map |
| 11 | `orama auth status` CLI | Yes, add it | — |
| 12 | Upgrade-prompt UI | Web banner on the existing localhost portal dashboard | tkinter fallback only when portal isn't running |
| 13 | Cert story for BUZZ mode | Same as #1 | — |

## The pluggable auth model (unchanged from the source plan, summarized)

`AuthProvider` protocol (`method`, `is_configured`, `get_auth_header`,
`verify_peer_auth`, `refresh_if_needed`) with four implementations —
`BearerTokenProvider` (the grandfathered default, always registered),
`BuzzNostrProvider`, `TwitterOAuthProvider`, `GoogleOAuthProvider`. An
`AuthManager` tries providers in priority order (BUZZ → Twitter → Google →
Bearer, Bearer always last) and falls back to Bearer Token if nothing else
is configured — **the mesh must never stop working because of an auth
change**. A `.orama/legacy_auth_mode` marker auto-creates on first run
after this update, suppressing nothing but triggering exactly one
non-blocking upgrade prompt per admin session; "keep using Bearer Token"
is always option 1, and "don't ask again" is always available.

Full provider source sketches (all four providers, `AuthManager`, the
upgrade-prompt CLI/GUI code, `secure_transport.py`'s TLS-context
construction, `peer_cert_manager.py`'s cert generation, `audit_log.py`'s
HMAC chain, and the `alphaclaw-tls` reverse proxy) are preserved verbatim
in the three source docs this entry ingests; re-derive from there when
implementation starts rather than re-designing from this summary, since
the source docs are implementation-ready, not just conceptual.

## What this plan explicitly does NOT decide

- Whether BUZZ/Twitter/Google auth ship simultaneously or are sequenced —
  the pluggable architecture supports any order; sequencing is an
  implementation-time call, not an architectural one.
- Exact CLI command names beyond `orama auth status`/`setup`/`finalize`
  (named in the source docs as illustrative, not final API).
- Whether `alphaclaw-tls` binds to a fixed port (3345 in the source
  sketch) or a discovered free port — a real deployment detail to settle
  when the package is actually built.

## Cross-repo coordination

This is an orama-system-led plan with two PT-side dependencies:
`alphaclaw-tls` (new PT package) and the `cryptography` library already
being a transitive dependency of PT's `endpoint-policy` package (verify
this is still true before relying on it as a zero-new-deps claim). Per the
task that produced this doc, a parallel PT branch/PR tracking the
`alphaclaw-tls` package specifically should be opened separately, cross-
referencing this doc by path (`orama-system/docs/v2/49-...`) rather than
duplicating the design here — PT's own `docs/adr/` or `docs/next/` is the
right home for that package's own implementation notes when it starts.
